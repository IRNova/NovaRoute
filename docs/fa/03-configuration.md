# ۳. پیکربندی

## متغیرهای محیطی

فایل `.env` در ریشهٔ نصب (`/opt/novaroute/.env`) خوانده می‌شود و `systemd` آن را به‌عنوان `EnvironmentFile` به فرایند می‌دهد.

### ضروری

| متغیر | توضیح |
|---|---|
| `JWT_SECRET` | کلید امضای کوکی نشست. اگر خالی باشد یک کلید تصادفی در `DATA_DIR/jwt-secret` ساخته می‌شود، ولی روی چند نمونه (`instance`) هماهنگ نخواهد بود. حداقل ۶۴ کاراکتر تصادفی بگذارید. |
| `INITIAL_PASSWORD` | رمز ورود تا وقتی رمزی در پنل ذخیره نشده. اگر خالی بماند مقدار پیش‌فرض `123456` است و ورود از راه دور با آن مسدود می‌شود. |
| `DATA_DIR` | محل پایگاه‌داده، پشتیبان‌ها و رازهای محلی. پیش‌فرض `~/.novaroute`. |

### امنیتی (به‌شدت توصیه‌شده)

| متغیر | توضیح |
|---|---|
| `API_KEY_SECRET` | کلید رمزگذاری میدانی. با تنظیم آن، `apiKey`، `accessToken`، `refreshToken` و `idToken` ارائه‌دهنده‌ها با `AES-256-GCM` روی دیسک رمز می‌شوند. بدون آن، همه چیز متن ساده است. |
| `MACHINE_ID_SALT` | نمک شناسهٔ ماشین برای توکن `CLI`. |
| `REQUIRE_API_KEY` | پیش‌فرض `true`. با `false` دروازه بدون کلید هم جواب می‌دهد، ولی فقط برای درخواست‌های محلی و شبکهٔ خصوصی. |
| `NR_ALLOW_ANONYMOUS_REMOTE_API` | تنها راه باز کردن دروازهٔ بدون کلید روی اینترنت. جز برای یک سرویس عمداً عمومی، تنظیمش نکنید. |
| `AUTH_COOKIE_SECURE` | پیش‌فرض هوشمند است (روی `HTTPS` پرچم `Secure` می‌گذارد). فقط اگر پشت پروکسی `TLS` هستید و کوکی نمی‌نشیند `false` کنید. |
| `ADMIN_MASTER_PASSWORD` | رمز اضطراری. همیشه کار می‌کند، پس بعد از بازیابی دسترسی حذفش کنید. |
| `NR_ALLOW_REMOTE_UNAUTH_API` | وقتی «ورود اجباری» خاموش است، اجازهٔ دسترسی مدیریتی از راه دور می‌دهد. خطرناک. |
| `TRUST_PROXY` | فقط وقتی پشت پروکسی معکوسی هستید که `X-Forwarded-For` را بازنویسی می‌کند. |

### اجرا و شبکه

| متغیر | توضیح |
|---|---|
| `PORT` / `HOSTNAME` | نشانی گوش‌دادن. `HOSTNAME=127.0.0.1` یعنی فقط پروکسی محلی به آن می‌رسد. |
| `BASE_URL` / `NEXT_PUBLIC_BASE_URL` | نشانی عمومی سرویس؛ برای بازگشت `OAuth` و کارهای داخلی لازم است. |
| `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY` | پروکسی خروجی برای تماس با ارائه‌دهنده‌ها (`socks5` هم پشتیبانی می‌شود). |
| `ENABLE_REQUEST_LOGS` | ثبت کامل درخواست‌ها. روی سرور مشترک خاموش بماند؛ محتوای پیام‌ها حساس است. |
| `OBSERVABILITY_ENABLED` | جمع‌آوری آمار مسیریابی. |
| `NR_AUTOBAN_THRESHOLD` / `NR_AUTOBAN_WINDOW_MS` / `NR_AUTOBAN_DURATION_MS` | تنظیم مسدودسازی خودکار `IP` پس از تلاش‌های ناموفق روی `/v1`. |

## تنظیمات داخل پنل

تنظیمات در جدول `settings` پایگاه‌داده ذخیره می‌شوند و روی متغیرهای محیطی اولویت دارند (متغیر محیطی فقط مقدار پیش‌فرض اولیه را می‌دهد).

### امنیت (`Settings > Security`)

| گزینه | پیش‌فرض | معنی |
|---|---|---|
| `Require Login` | روشن | داشبورد بدون ورود باز نشود |
| `Require API Key` | روشن | هر تماس `/v1` باید کلید معتبر داشته باشد |
| ورود دومرحله‌ای (`TOTP`) | خاموش | پس از رمز، کد یک‌بارمصرف بخواهد |
| دسترسی داشبورد از تونل | روشن | اگر تونل عمومی دارید، خاموشش کنید |

### ارائه‌دهنده‌ها

هر ارائه‌دهنده یک یا چند «اتصال» (`connection`) دارد. برای هر اتصال می‌توانید چند حساب اضافه کنید؛ در صورت خطا یا اتمام سهمیه، موتور به حساب بعدی می‌رود.

سه نوع اعتبارنامه:
- **کلید `API`**: ساده‌ترین حالت.
- **`OAuth`**: از داشبورد جریان ورود را باز می‌کنید و توکن‌ها خودکار تازه می‌شوند.
- **`Cookie`**: نشست مرورگر برای ارائه‌دهنده‌های وب؛ شکننده‌ترین حالت و بیشترین احتمال خرابی.

### کامبو (`Combos`)

کامبو یعنی یک نام مدل که پشتش فهرستی از مدل‌های واقعی است. راهبردها:

| راهبرد | رفتار |
|---|---|
| `fallback` | به ترتیب، تا اولین پاسخ موفق |
| `round-robin` چسبنده | چرخشی با چسبندگی به تعداد درخواست مشخص |
| `cost-optimized` | ارزان‌ترین گزینهٔ سازگار با نیاز درخواست |
| `fusion` / `pipeline` | ترکیب چند مدل روی یک درخواست |

### سقف نرخ و سقف هزینهٔ هر کلید

هر کلید می‌تواند چهار سقف داشته باشد و هر چهار مورد در مسیر همهٔ درخواست‌ها اعمال می‌شوند، نه فقط گفتگو:

| سقف | میدان | رفتار در صورت عبور |
|---|---|---|
| هزینهٔ روزانه (دلار) | `dailyUsageLimitUsd` | پاسخ `429` تا شروع پنجرهٔ بعد |
| هزینهٔ هفتگی (دلار) | `weeklyUsageLimitUsd` | پاسخ `429` |
| درخواست در دقیقه | `rpmLimit` | پاسخ `429` با هدرهای `Retry-After` و `X-RateLimit-*` |
| درخواست هم‌زمان | `concurrencyLimit` | پاسخ `429` |

سقف‌های هزینه از تاریخچهٔ مصرف خوانده می‌شوند و پس از ری‌استارت هم برقرارند. سقف‌های نرخ در حافظهٔ فرایند نگه داشته می‌شوند (پنجرهٔ لغزان یک‌دقیقه‌ای) و با ری‌استارت صفر می‌شوند؛ این عمدی است تا مسیر داغ درخواست به پایگاه‌داده نخورد.

تنظیم از داشبورد: `Dashboard > API Keys` هنگام ساخت کلید، یا بعداً از `‎/api/keys/[id]/usage-limits`. وضعیت زنده در برگهٔ `Rate Limits` صفحهٔ `Usage` دیده می‌شود.

### کلیدهای دروازه

- `Dashboard > API Keys`: هر کلاینت کلید جدا بگیرد تا بتوانید مصرف را تفکیک و کلید را جدا باطل کنید.
- کلیدها می‌توانند تاریخ انقضا و دامنهٔ دسترسی (`scope`) داشته باشند؛ `manage` و `admin` اجازهٔ کار با `API` مدیریتی می‌دهند.
- «کلید مجازی» (`sk-novaroute-...`) برای کاربران نهایی با سقف هزینه است.

## کاربران و نقش‌ها

تا پیش از این، پنل یک هویت داشت: هر کسی رمز را می‌دانست می‌توانست کلید `API` بسازد، دیتابیس را بازیابی کند و به‌روزرسانی کد را اجرا کند. حالا حساب کاربری با سه نقش وجود دارد:

| نقش | چه می‌تواند بکند |
|---|---|
| `admin` | همه چیز، شامل کاربران، کلیدها، دیتابیس، به‌روزرسانی و تنظیمات امنیتی |
| `operator` | کار روزمره: ارائه‌دهنده‌ها، کامبوها، مدل‌ها، مصرف و عامل. بدون دسترسی به کلیدها، کاربران، دیتابیس و به‌روزرسانی |
| `viewer` | فقط خواندن، و آن هم نه بخش‌های حاوی اعتبارنامه (کلیدها، کاربران، سیاههٔ رخدادها، دیتابیس) |

مدیریت از `Settings > Security > Users`. نکته‌های مهم:

- نصب‌های موجود دست‌نخورده کار می‌کنند: مهاجرت شمارهٔ ۱۱ رمز مشترک فعلی را به یک حساب `admin` منتقل می‌کند و ورود با همان رمز (بدون نام کاربری) همچنان کار می‌کند.
- ورود با نام کاربری هم پذیرفته می‌شود: `{"username":"sara","password":"..."}`.
- آخرین حساب `admin` فعال را نمی‌شود حذف، غیرفعال یا تنزل درجه داد؛ پاسخ `409` می‌گیرید.
- نشست‌هایی که پیش از این تغییر ساخته شده‌اند نقش `admin` دارند، یعنی دقیقاً همان اختیاری که قبلاً داشتند.

## رصدپذیری و ثبت رخداد

**سنجه‌ها (`Prometheus`)**: نقطهٔ پایانی `‎/api/metrics` خروجی استاندارد `Prometheus` می‌دهد: تعداد درخواست، توکن و هزینهٔ ۲۴ ساعت گذشته به تفکیک ارائه‌دهنده، مدل و کلید؛ وضعیت زندهٔ سقف نرخ هر کلید؛ تعداد اتصال‌های فعال؛ و آمار فرایند.

چون یک `scraper` نمی‌تواند وارد داشبورد شود، متغیر `METRICS_TOKEN` را تنظیم کنید:

```yaml
scrape_configs:
  - job_name: novaroute
    metrics_path: /api/metrics
    authorization:
      credentials: "<METRICS_TOKEN>"
    static_configs:
      - targets: ["gateway.example.com"]
```

بدون این متغیر، نقطهٔ پایانی همچنان کار می‌کند ولی فقط با نشست داشبورد یا کلید دارای دامنهٔ `manage`. هیچ‌وقت ناشناس نیست: نام مدل‌ها و هزینه‌ها دادهٔ کسب‌وکار است.

**ردیابی (`OpenTelemetry`)**: با تنظیم یک نقطهٔ پایانی، هر تماس دروازه یک `span` می‌شود:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318
OTEL_EXPORTER_OTLP_HEADERS=x-api-key=abc    # اختیاری
OTEL_SERVICE_NAME=novaroute                 # اختیاری
```

هیچ وابستگی جدیدی لازم نیست؛ خروجی `OTLP/HTTP JSON` مستقیم ساخته و ارسال می‌شود و با `Grafana Alloy`، `otel-collector`، `Tempo`، `Jaeger` و مشابه‌ها کار می‌کند. نام صفت‌ها طبق قرارداد `gen_ai.*` است: `gen_ai.system`، `gen_ai.request.model`، `gen_ai.usage.input_tokens` و `gen_ai.usage.output_tokens`، به‌علاوهٔ `novaroute.cost_usd`.

اگر این متغیر تنظیم نباشد، ردیابی کاملاً خاموش است و هیچ هزینه‌ای روی مسیر درخواست ندارد. اگر `collector` خاموش باشد، فقط یک بار هشدار در لاگ می‌آید و سرویس بدون اختلال ادامه می‌دهد.

**ثبت رخداد اقدام‌های مدیریتی**: هر تماس تغییردهنده به مسیرهای مدیریتی ثبت می‌شود (روش، مسیر، عامل، `IP`، زمان و اینکه مسیر حساس است یا نه). خواندن‌ها ثبت نمی‌شوند. آخرین ۵۰۰ رخداد در `Settings > Security` و از `‎/api/security/audit` در دسترس است. توجه: ثبت پیش از اجرای مسیر انجام می‌شود، پس تلاش‌های ناموفق هم دیده می‌شوند؛ این عمدی است.

**سنجش کارایی**: `npm run bench` سربار خود دروازه را اندازه می‌گیرد (نه زمان مدل). با `--model` می‌توانید یک تماس واقعی را هم بسنجید.

## کانال‌های پیام‌رسان

چهار آداپتور اختصاصی وجود دارد (`Telegram`، `WhatsApp`، `Slack`، `Discord`) و یک آداپتور عمومی به نام `webhook` که هر سکوی دیگری با `API` مبتنی بر `HTTP` را پوشش می‌دهد: `Matrix`، `Mattermost`، `Rocket.Chat`، `Teams`، درگاه پیامک، پل `signal-cli` و هر چیز مشابه.

ساخت یک کانال عمومی:

```bash
curl -X POST http://localhost:20126/api/channels \
  -b "auth_token=..." -H 'content-type: application/json' \
  -d '{
    "type": "webhook",
    "name": "matrix-bridge",
    "config": {
      "textPath": "message.body",
      "senderPath": "sender",
      "chatPath": "room_id",
      "outboundUrl": "https://matrix.example.org/_matrix/client/r0/rooms/.../send",
      "bodyTemplate": "{\"msgtype\":\"m.text\",\"body\":\"{{text}}\"}"
    },
    "credentials": { "headers": { "Authorization": "Bearer ..." } }
  }'
```

پاسخ شامل `inboundPath` و یک `secret` است. سکوی مقابل باید پیام‌های ورودی را به همان مسیر بفرستد و راز را در هدر `X-Channel-Secret` بگذارد؛ این تنها چیزی است که جلوی آن نقطهٔ پایانی ایستاده، پس مثل هر راز دیگری با آن رفتار کنید.

تعریف کانال‌ها در پایگاه‌داده ذخیره می‌شود، پس کانال و نشانی ورودی‌اش بعد از ری‌استارت و استقرار مجدد باقی می‌مانند.

## پرونده‌های حساس روی دیسک

| مسیر | محتوا |
|---|---|
| `DATA_DIR/db/data.sqlite` | همهٔ تنظیمات و اعتبارنامه‌ها |
| `DATA_DIR/jwt-secret` | کلید امضای نشست (اگر متغیر محیطی نباشد) |
| `DATA_DIR/auth/cli-secret` | راز توکن `CLI` |
| `DATA_DIR/machine-id` | شناسهٔ پایدار ماشین |
| `INSTALL_DIR/.env` | همهٔ رازهای محیطی |

هر پنج مورد باید فقط برای کاربر سرویس خواندنی باشند (`chmod 600`).
